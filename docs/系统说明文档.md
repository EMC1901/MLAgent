## 1. 系统定位与论文背景对应关系

### 1.1 MatAIDE 是什么

MatAIDE 是一个面向材料科学研究的**自主端到端机器学习建模系统**。它不是一个普通的 AutoML 工具或简单的 Web 建模平台，而是一个将 **LLM（大语言模型）驱动的 AI reasoning kernel** 深度嵌入材料机器学习全流程的智能系统。

代码层面，系统名为 MLAgent（见 `backend/app/main.py:30`），论文中命名为 MatAIDE。系统通过 FastAPI 后端 + React 前端的 Web 架构，使用 PostgreSQL 持久化状态，在 Docker 容器中运行。

### 1.2 解决的核心问题

传统材料机器学习面临三个关键瓶颈：

1. **建模决策不透明**：材料科学家需要理解"为什么选择这个算法""为什么这样处理数据"，但现有 AutoML 工具是黑箱决策；
2. **工作流不可复现**：从原始数据到最终模型的完整过程难以追溯和复现；
3. **领域知识缺位**：通用 AutoML 工具不了解材料科学特有的特征工程（如元素性质描述符、组成特征）、物理约束和评估需求。

### 1.3 与普通 AutoML / Web 平台的区别

| 维度 | 普通 AutoML | 普通 Web ML 平台 | MatAIDE |
|---|---|---|---|
| 工作流构建 | 固定 pipeline | 用户手动配置 | **LLM 根据数据特征自动规划** |
| 决策解释 | 无 | 无 | **每个关键决策附有 rationale**（含材料科学依据） |
| 特征工程 | 通用方法 | 通用方法 | **材料专用 featurizer 注册表**（matminer/pymatgen/自定义） |
| 迭代优化 | 固定轮次 | 无 | **LLM 根据证据自主决策 iterate/stop** |
| 可复现性 | 弱 | 弱 | **全链路 artifact 保存 + reproducibility summary** |
| 材料领域知识 | 无 | 无 | **物理约束检查、材料特征保护、领域 rationale** |

### 1.4 Autonomous end-to-end modeling 的代码体现

系统从用户上传数据到生成最终报告，**全部由 LLM 规划的 workflow 自动驱动**。核心流程代码见 `backend/app/main.py:58-72` 中注册的 15 个模块路由，覆盖了从 `task_specification` → `task_interpretation` → `dataset_profile` → `workflow_planning` → `feature_engineering` → `feature_preprocessing` → `model_search_context` → `pipeline_generation` → `pipeline_execution` → `metric_evaluation` → `iteration_decision` → `workflow_refinement` → `interpretability_analysis` → `final_output` 的完整链路。

### 1.5 Decision-level explanation 的代码体现

系统的"解释"发生在两个层面：

- **模型层面**：SHAP、permutation importance、partial dependence、coefficient importance 等（`interpretability_analysis/` 模块）
- **工作流层面**：每个 LLM 驱动的决策模块都输出 `decision_rationale` + `workflow_rationale` + `reasoning` 结构，说明**为什么**选择某个数据处理策略、算法和评估方法（`workflow_planning/`, `iteration_decision/`, `model_search_context/` 等模块）

## 3. 端到端工作流程

### 3.1 完整流程概述

系统工作流分为 **7 个阶段、约 15 个处理步骤**，每个步骤可独立触发，也可通过前端自动串联执行。

### 3.2 各步骤详细说明

#### 步骤 1: 用户任务定义（task_specification）

- **用户操作**：通过 `TaskSpecificationPage` 填写任务名称、描述、预测目标、数据来源等
- **代码位置**：`backend/app/modules/task_specification/service.py` — `TaskSpecificationService.create_task()`
- **前端组件**：`frontend/src/modules/taskSpecification/pages/TaskSpecificationPage.tsx`
- **输入**：JSON 格式的任务规范（名称、描述、材料体系、预测目标、约束条件等）
- **输出**：持久化的 TaskSpecification 记录（状态：draft → valid/valid_with_warning）
- **数据库模型**：`backend/app/modules/task_specification/model.py`

#### 步骤 2: LLM 任务解释（task_interpretation）

- **触发**：用户在前端点击"开始解释"
- **代码位置**：
  - `backend/app/modules/task_interpretation/service.py:45` — `create_interpretation()`
  - `backend/app/modules/task_interpretation/prompt_builder.py` — 构建 LLM prompt
  - `backend/app/modules/task_interpretation/parser.py` — 解析 LLM JSON 输出
- **LLM 调用**：`backend/app/modules/task_interpretation/llm_client.py` — `LLMClient.generate()`
- **输入**：TaskSpecification 的 JSON 上下文（通过 `task_spec_adapter.py:adapt_task_spec()` 转换）
- **输出**：结构化的 TaskInterpretation，包括：
  - `interpreted_task_type`（regression / classification / ranking）
  - `interpreted_input_modality`（composition / structure / descriptor / text / mixed）
  - `interpreted_material_domain`
  - `interpreted_prediction_target`（含 target_category、target_unit 等）
  - `modeling_intent`（primary_goal、optimization_direction、preferred_metric）
  - `planning_hint`（task_family、input_representation、是否需要特征工程/可解释性）
  - `constraint_interpretation`
  - `recommended_defaults`（evaluation_metric、validation_strategy）
  - `ambiguities` + `warnings`
- **Schema 定义**：`backend/app/modules/task_interpretation/schemas.py`
- **论文意义**：体现系统**理解材料科学任务上下文**的能力，而非简单的关键字匹配

#### 步骤 3: 数据画像（dataset_profile）

- **代码位置**：
  - `backend/app/modules/dataset_profile/service.py` — 负责编排
  - `backend/app/modules/dataset_profile/profiler.py` — 核心画像逻辑
  - `backend/app/modules/dataset_profile/checkers/` — schema / modality / quality / target 检查器
  - `backend/app/modules/dataset_profile/loaders/` — file_loader（CSV/XLSX）+ matbench_loader
- **数据加载**：支持 CSV 和 XLSX 格式（配置见 `settings.py:26`），最大 100MB
- **输出**：DatasetProfile JSON，包括：
  - `dataset_schema`：列名、类型、基本统计
  - `modality_check`：输入模态识别结果
  - `target_profile`：目标变量分析（分布、异常值等）
  - `data_quality`：缺失值统计、重复行检测、常数列检测
  - `profiling_summary`：可用性判断（`is_usable_for_ml`）
  - `workflow_planning_input`：供下游 workflow_planning 使用的数据摘要
- **论文意义**：系统能**自动评估数据质量**并在质量不足时给出警告

#### 步骤 4: LLM 工作流规划（workflow_planning）★ 核心 AI 推理步骤 ★

- **代码位置**：
  - `backend/app/modules/workflow_planning/service.py:62` — `create_plan()`
  - `backend/app/modules/workflow_planning/context_builder.py` — 聚合 task + interpretation + dataset 三层上下文
  - `backend/app/modules/workflow_planning/prompt_builder.py` — 构建包含 featurizer registry 的完整 prompt
- **输入**：整合了 TaskSpecification + TaskInterpretation + DatasetProfile 的完整上下文
- **LLM 输出**（Schema 定义于 `prompt_builder.py:10-28`）：
  - `task_summary`：任务类型、输入模态、预测目标确认
  - `data_strategy`：输入列、目标列、清洗步骤、缺失值策略
  - `feature_strategy`：选择/拒绝哪些 featurizer、含 `decision_rationale`（reason + evidence + material_science_basis + expected_benefit + risk + fallback）
  - `preprocessing_intent`：预处理意图（是否需要标准化、编码等）
  - `model_strategy`：候选模型族、选择理由、排除理由
  - `validation_strategy`：数据划分策略（holdout / k-fold / stratified k-fold）
  - `evaluation_strategy`：评估指标选择
  - `hpo_strategy`：超参数优化策略（Grid / Random / Bayesian / Optuna）
  - `interpretability_strategy`：可解释性方法选择
  - `pipeline_generation_input`：pipeline 步骤 + 必需组件
  - `workflow_rationale`：整体工作流设计的**全局理由**（含材料科学依据）
- **论文意义**：这是 MatAIDE 区别于传统 AutoML 的**核心体现**——系统不光选择算法，还**解释为什么**这样选择

#### 步骤 5: 特征工程（feature_engineering）

- **代码位置**：
  - `backend/app/modules/feature_engineering/service.py`
  - `backend/app/modules/feature_engineering/strategy_resolver.py` — 解析 workflow_plan 的 feature_strategy
  - `backend/app/modules/feature_engineering/feature_matrix_builder.py` — 执行特征生成
  - `backend/app/modules/feature_engineering/featurizers/` — 各类 featurizer 实现
- **支持的 Featurizer**（见 `shared/registry/featurizer_registry.py`）：
  - `basic_composition` — 内置 103 元素性质统计
  - `pymatgen_composition_parser` — 使用 pymatgen 解析化学式
  - `matminer_stoichiometry` — 化学计量特征
  - `matminer_element_property` — 132 个元素性质统计特征
  - `matminer_magpie` — 132 个 Magpie 描述符
  - `matminer_valence_orbital` — 价轨道特征
  - `descriptor_passthrough` — 现有描述符直通
  - `descriptor_cleaner` — 描述符清洗
  - `structure_placeholder` / `matminer_structure_basic` — 结构特征（计划中）
- **Featurizer 路由**：`featurizer_router.py` 桥接注册表 ID 和可执行类
- **输出**：特征矩阵（Parquet 格式）+ 特征元数据

#### 步骤 6: LLM 规划的预处理（feature_preprocessing）

- **代码位置**：
  - `backend/app/modules/feature_preprocessing/service.py`
  - `backend/app/modules/feature_preprocessing/llm_planner.py` — **LLM 生成 PreprocessingPlan**
  - `backend/app/modules/feature_preprocessing/plan_executor.py` — 执行计划
  - `backend/app/modules/feature_preprocessing/preprocessing_executor.py` — 执行器
  - `backend/app/modules/feature_preprocessing/preprocessors/` — imputer / scaler / encoder / feature_selector
- **LLM Planner 特点**：
  - 使用 **Feature Preprocessing Capability Registry**（`shared/registry/fp_capability_registry.py`）约束 LLM 只能选择已实现的操作
  - LLM 输出包含每个操作的 `decision_rationale`（reason + evidence + expected_benefit + risk + fallback）
  - 强制操作顺序：泄漏检测 → 缺失分析 → 低信息过滤 → 插补 → 分布变换 → 缩放 → 相关性处理 → 特征选择 → 降维
  - 防止数据泄漏（`fit_scope` 强制为 `fold_only`）
- **预处理能力注册表**（`fp_capability_registry.py`）包括：
  - `median_imputer` / `mean_imputer` / `constant_imputer`
  - `standard_scaler` / `minmax_scaler` / `robust_scaler`
  - `onehot_encoder` / `ordinal_encoder`
  - `variance_threshold_selector` / `correlation_filter` / `mutual_info_selector`
  - `pca_reducer`
  - `target_encoder`
- **输出**：model_ready 特征矩阵（Parquet）+ 预处理器（joblib）+ 特征元数据

#### 步骤 7: LLM 模型搜索上下文（model_search_context）

- **代码位置**：
  - `backend/app/modules/model_search_context/service.py:51` — `create_model_search_context()`
  - `backend/app/modules/model_search_context/llm_strategy_advisor.py` — LLM 策略顾问
  - `backend/app/modules/model_search_context/candidate_model_selector.py` — 候选模型选择
  - `backend/app/modules/model_search_context/search_space_builder.py` — 搜索空间构建
- **LLM 输入**：数据集分析结果 + 特征组分析 + 预处理结果 + 原始策略
- **LLM 输出**：
  - 模型策略调整建议（增加/减少/替换模型候选）
  - HPO 策略调整（搜索方法、trial 分配、搜索空间）
  - 验证和评估策略调整
- **系统验证**：LLM 输出经 `validate_llm_advice()` 验证后再合并
- **候选模型选择**：基于 16 个模型族的注册表（`shared/registry/model_registry.py`），根据任务类型、数据规模、特征数量等过滤
- **GOFEE 子系统**：HPO 深度推理系统（`model_search_context/` 中独立子系统），包含搜索空间推理、参数图构建

#### 步骤 8: Pipeline 生成（pipeline_generation）

- **代码位置**：`backend/app/modules/pipeline_generation/service.py:56` — `create_pipeline_generation()`
- **流程**：
  1. 构建上游上下文
  2. 解析 artifacts（模型、预处理结果等）
  3. 绑定组件（模型 + 预处理器 + 评估器）
  4. 构建 pipeline specs（含 baseline + HPO candidate）
  5. 构建 trial plan
  6. 验证 pipeline（完整性、一致性、安全性）
  7. 可选 LLM advisory review（审查 pipeline 合理性）
  8. 构建 execution input
- **LLM 审查**（可选）：`llm_pipeline_reviewer.py` 审查 pipeline 并给出建议

#### 步骤 9: Pipeline 执行（pipeline_execution）

- **代码位置**：`backend/app/modules/pipeline_execution/service.py`
- **功能**：
  - 执行模型训练（支持 k-fold 交叉验证）
  - 执行 HPO 搜索（支持 search_space_plan）
  - 管理训练日志、模型保存
  - 追踪每个 trial 的状态

#### 步骤 10: 指标评估（metric_evaluation）

- **代码位置**：
  - `backend/app/modules/metric_evaluation/service.py`
  - `backend/app/modules/metric_evaluation/metric_calculator.py` — 指标计算
  - `backend/app/modules/metric_evaluation/metric_registry.py` — 指标注册表
  - `backend/app/modules/metric_evaluation/baseline_comparator.py` — 基线比较
  - `backend/app/modules/metric_evaluation/model_ranker.py` — 模型排名
- **回归指标**：MAE, RMSE, R², MAPE, Max Error, Explained Variance
- **分类指标**：Accuracy, Precision, Recall, F1, ROC-AUC, Log Loss
- **输出**：按 CV fold 聚合的指标 + 模型排名 + 最佳模型标识

#### 步骤 11: LLM 迭代决策（iteration_decision）★ 核心 AI 推理步骤 ★

- **代码位置**：`backend/app/modules/iteration_decision/service.py:57` — `create_decision()`
- **六阶段流程**：
  1. **Gather context**（零 LLM）：收集 metrics、upstream、history
  2. **Extract evidence**（零 LLM）：从性能指标、材料科学、工作流质量、历史趋势提取证据
  3. **System rule checks**（零 LLM）：ML 规则检查（过拟合、欠拟合、基线比较）+ 材料规则检查（物理约束、化学空间覆盖）+ 安全规则检查（最大迭代次数、无改进趋势）
  4. **Build LLM context**：聚合所有上下文
  5. **LLM decision**（单次 LLM 调用）：`llm/decision_maker.py` — 输出 iterate/stop 决策 + reasoning + evidence_basis + iteration_plan/stop_rationale
  6. **Build plans**：若 iterate，构建 revised_workflow_plan + iteration_rerun_plan
- **LLM 决策输出**（schema 见 `llm/prompt_builder.py`）：
  - `decision`：iterate / stop
  - `reasoning`：包含 `task_completion`, `performance_assessment`, `gap_analysis`, `root_cause`（识别性能不足的根因维度：feature_side / model_side / data_side / evaluation_side）, `improvement_potential`, `final_reasoning_summary`
  - `iteration_plan`（若 iterate）：`rerun_from_stage`（从哪个阶段重新执行）, `stage_changes`（各阶段改动 + rationale）, `preserved_stages`, `expected_improvement`, `stop_condition`
  - `stop_rationale`（若 stop）：停止原因 + 类别（goal_achieved / diminishing_returns / resource_limit / convergence_failure）
  - `confidence`：low / medium / high
- **Fallback 机制**：当 LLM 不可用时，系统使用规则引擎（`_rule_based_fallback()`）推断决策

#### 步骤 12: LLM 工作流优化（workflow_refinement）

## 4. AI Reasoning Kernel 的实现与作用

### 4.1 概述

MatAIDE 的 AI reasoning kernel **不是一个单一模块**，而是**分布在整个工作流中的 LLM 调用网络**。系统在 6 个关键决策点调用 LLM 进行推理和决策：

| # | 模块 | LLM 调用 | 决策类型 | 代码位置 |
|---|---|---|---|---|
| 1 | task_interpretation | 1 次 | 理解任务语义 | `task_interpretation/service.py:65` |
| 2 | workflow_planning | 1 次 | 设计完整工作流 | `workflow_planning/service.py:77` |
| 3 | feature_preprocessing | 1 次 | 规划预处理操作 | `feature_preprocessing/llm_planner.py` |
| 4 | model_search_context | 1 次 | 调整模型/HPC策略 | `model_search_context/service.py:146` |
| 5 | pipeline_generation | 可选 1 次 | 审查 pipeline | `pipeline_generation/service.py:179` |
| 6 | iteration_decision | 1 次 | 决定迭代/停止 | `iteration_decision/service.py:174` |
| 7 | workflow_refinement | 1 次 | 生成改进方案 | `workflow_refinement/service.py` |
| 8 | result_diagnosis | 1 次 | 诊断性能问题 | `result_diagnosis/service.py` |
| 9 | interpretability_analysis | 1 次 | 总结解释结果 | `interpretability_analysis/service.py` |
| 10 | final_output | 1 次 | 撰写最终报告 | `final_output/service.py:175` |

### 4.2 各阶段调用详情

#### 阶段 A：任务理解（task_interpretation）

#### 阶段 E：迭代决策（iteration_decision）★ 最核心的 AI 推理 ★

#### 阶段 G：最终报告（final_output）
- **LLM Report Writer**：`backend/app/modules/final_output/llm_report_writer.py`
- **输入**：全链路摘要（task, data, workflow, model, metrics, interpretability, reproducibility）
- **输出**：结构化报告（含局限性、材料科学洞察）

### 4.3 AI Reasoning Kernel 的核心设计原则

#### 4.3.1 "Registry-Constrained" LLM 生成
LLM 不是自由生成，而是被**注册表（Registry）严格约束**：
- 只能从 `model_registry.py` 中选择已注册的模型
- 只能从 `featurizer_registry.py` 中选择已实现的 featurizer
- 只能从 `fp_capability_registry.py` 中选择已实现的预处理操作
- 所有 Registry 在 prompt 中以 JSON 形式提供给 LLM

#### 4.3.2 "Evidence-Driven" 决策
LLM 不是凭空推理，而是被提供**结构化的多维度证据**：
- `ml_evidence`：性能指标对比、过拟合/欠拟合检测、学习曲线特征
- `materials_evidence`：物理约束违反、化学空间覆盖、材料特征相关性
- `workflow_evidence`：Pipeline 完整性、Artifact 可用性
- `history_evidence`：历史迭代趋势、重复根因

#### 4.3.3 "System-Validated" LLM 输出
每个 LLM 输出都经过**多层验证**：
- **Parse**：JSON 解析 → 结构验证
- **Validate**：代码级验证（禁止的字段、不合理的参数）
- **Normalize**：标准化到内部 Schema
- **Fallback**：LLM 失败时使用规则引擎

#### 4.3.4 "Full-Traceability" 决策记录
每次 LLM 调用都持久化以下内容：
- `llm_request_json`：完整的 prompt（system + user）
- `llm_response_json`：原始 LLM 输出
- `reasoning_json`：解析后的结构化推理
- `decision_rationale`：每个操作的决策理由

#### 8.1.2 特征组分析

`feature_group_analyzer.py` 按 lineage 对特征分组（如 "composition_descriptors", "magpie_descriptors", "element_property" 等），分析每组的整体重要性。这对材料科学用户理解"哪类特征最重要"特别有价值。

#### 8.1.3 物理约束检查

`physics_constraint_checker.py` 检查模型预测是否违反已知的物理约束（如单调性、边界条件等）。

### 8.2 工作流层面的解释（决策级解释）

这是 MatAIDE 的核心创新。系统在多个环节输出 `decision_rationale`：

#### WorkflowPlan 中的 rationale

在 `workflow_planning` 的输出中：
- `feature_strategy.selected_feature_actions[].decision_rationale`：为什么选择某个 featurizer（含 `material_science_basis`）
- `feature_strategy.rejected_feature_actions`：为什么拒绝某个 featurizer
- `workflow_rationale`：整体工作流设计的全局理由
- API 端点：`GET /workflow-plan/{plan_id}/feature-strategy-rationale`（见 `workflow_planning/api.py`）

#### PreprocessingPlan 中的 rationale

在 `feature_preprocessing/llm_planner.py` 的输出中：
- 每个 `operation_sequence[]` 条目都有 `decision_rationale`（reason + evidence + expected_benefit + risk + fallback）
- `rejected_operations[]`：为什么拒绝某些操作（含 reason + evidence）

#### IterationDecision 中的 reasoning

在 `iteration_decision` 的输出中：
- `reasoning` 包含 `root_cause` 分析（识别性能不足的根因维度）
- `iteration_plan.stage_changes` 中每个改动都有 `rationale`

#### LLM Interpretability Summary

在 `interpretability_analysis/llm_interpretability_summarizer.py` 中：
- 基于所有计算结果生成自然语言解释
- 包含对材料科学含义的讨论

### 8.3 三个层面的区分

| 层面 | 内容 | 代码位置 | 论文意义 |
|---|---|---|---|
| **模型层解释** | 为什么模型预测某个值（SHAP, feature importance） | `interpretability_analysis/` | 预测层面的可解释性 |
| **工作流层解释** | 为什么选择某个算法/预处理（decision_rationale） | `workflow_planning/`, `iteration_decision/`, `feature_preprocessing/llm_planner.py` | **决策层面的可解释性（核心创新）** |
| **报告层叙事** | 自动生成的自然语言解释 | `final_output/llm_report_writer.py`, `interpretability_analysis/llm_interpretability_summarizer.py` | 用户可读性 |

**5. Decision-Level Explanation Across Two Scales**

> Beyond model-level interpretability (SHAP, permutation importance, partial dependence), MatAIDE provides workflow-level explanations: why a particular featurizer was chosen, why a model family was recommended, why the system decided to iterate or stop. | **reproducible machine learning workflows** | ✅ 部分支持 | artifact 保存 + LLM request/response 记录 + reproducibility_summary | **中等** | 缺少显式随机种子管理（未在代码中确认）。需补充或谨慎表述 |
| **predictive reliability** | ✅ 支持 | cross-validation + baseline comparison + multi-metric evaluation | **强** | 建议补充 uncertainty quantification |
| **adaptability across datasets** | ✅ 部分支持 | LLM 根据数据特征调整策略 | **中等** | 系统的 adaptivity 主要依靠 LLM 的推理能力，缺乏跨任务的经验学习（meta-learning）。需在 limitation 中提及 |
| **usability for materials researchers** | ✅ 部分支持 | 前端提供了完整的操作界面 | **中等** | 前端为开发者导向（JSON 展示为主），不是面向领域科学家的优化 UI。可在论文中说明当前版本为研究原型 |

### 14.1 需要特别关注的 gap

1. **随机种子未显式管理**：在 `settings.py` 和模型训练代码中未发现全局随机种子设置。如果论文强调 "reproducible"，需要添加这一机制。

2. **前端 UI 的领域适配度**：当前前端大量展示 JSON 原始数据，对于不熟悉 JSON 的材料科学家可能不够友好。建议在论文的 Discussion 中提及此限制。

3. **缺少 ablation study 支持**：代码中没有明确的支持 ablation study 的基础设施（如"关闭 LLM planning 使用默认策略"的对比模式）。但通过选择不调用 LLM（`use_llm_advisor=False`）可以实现部分对比。

4. **跨任务知识迁移未实现**：系统为每个任务独立运行，不会从历史任务中学习。如果论文中提到了 "learning from experience"，需要修正。

5. **GOFEE 子系统状态**：`model_search_context/` 中有 GOFEE 相关代码（HPO 深度推理），但部分状态为 `planned`。需要确认哪些功能已在当前版本中可用。
